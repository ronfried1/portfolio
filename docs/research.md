## Case structure

**Landly** follows a landowner from an identifier to planning context, establishes Ron’s platform responsibility, compares direct lookup with place-based browsing, identifies the public result and explains the difference between a geographic key and a human entry point. The tradeoff is observable in the public product. It does not establish who first proposed each feature.

**FastRide** follows a visitor who needs the same ticket after refreshing. The article identifies the existing API boundary, contrasts in-memory and local persistence, describes duplicate requests and expiry, and explains the cross-device limit. The outcomes are visible code paths. The original live demo returned its application shell without ride inventory during the audit.
